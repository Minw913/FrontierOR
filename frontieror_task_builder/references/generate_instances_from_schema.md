# Generate Instances From Schema

Use in Flow 2, Flow 3, and Flow 4 when there is no paper-derived `all_instances.json`.

## Inputs

- confirmed `problem_description.txt`
- confirmed `original_formulation.tex`
- `instance_schema.json`
- `solution_schema.json`
- optional submitter scale notes

## Outputs

- `generate_multiple_instances.py`
- `instance/tiny_instance.json`
- `instance/large_instance_1.json`
- `instance/large_instance_2.json`
- `instance/large_instance_3.json`
- `instance/large_instance_4.json`
- `instance/large_instance_5.json`

## Generator Requirements

- Use deterministic seeds.
- Put all instance generation in `generate_multiple_instances.py`.
- Create `instance/` before writing files.
- Write exactly the canonical layout unless the user asks otherwise.
- All generated instance files must have the same field names and structure.
- Document scale choices and parameter settings at the top of the script.
- Do not depend on `all_instances.json`.

## Feasibility Requirements

Each instance must be generated by construction or through rejection sampling with explicit feasibility prechecks. If random generation is used:

- define a deterministic seed iteration rule;
- retry until feasibility prechecks pass;
- use a sufficiently large retry budget;
- write a JSON file only after checks pass.

Prechecks should enforce obvious necessary conditions from the formulation, such as demand/capacity compatibility, connectedness, resource availability, time-window reachability, or budget sufficiency as applicable.

## Scale Requirements

- `tiny` must be a smoke-test instance that solves quickly.
- `large_1` through `large_5` must be meaningful large-scale instances.
- Large instances should vary along structural or parametric diversity dimensions, not only random seed.
- Keep all scales realistic for the problem domain.
